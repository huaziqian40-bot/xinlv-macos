# 心履 电脑版 · 交接文档

> JavaFX 桌面客户端（Windows + macOS），心情记录 / 树洞 / 日历 / 徽章。
> 仓库：`D:\moodsite\windows` 与 `D:\moodsite\macos`（**同一套代码**）
> 当前版本：**1.1.10**　本文最后核对：2026-10-12

---

## 1. 这条线负责什么、不负责什么

**负责**：心履**电脑版**这个客户端 —— Windows 与 macOS 两个仓库、它的界面、
本地数据、与两个服务端的通信、自动更新、打包与发布。

**不负责**（都是独立开发线）：

- **心履 安卓版**：`D:\moodsite\android`。
- **心履 网页端**：`D:\moodsite\web`（Django 服务端 + 服务端渲染的页面）。
- **心履服务端本身**：`D:\moodsite\web` 里的 `core/` 是服务端代码。
- **phix 服务端 / 官网 / PHL 系列**。

⚠️ **两个仓库是同一个产品**，不是两个产品。共有文件必须**逐字节一致**，
只有这些文件**允许**不同：

| 平台专属 | 说明 |
|---|---|
| `updater/Updater.java` vs `updater/UpdaterMac.java` | 两个平台的更新实现 |
| `about/About.java` | 薄壳，唯一差异是引用上面哪一个 |
| 图标等资源 | `logo.ico` / macOS 图标 |
| `Main.java` 的平台分支 | 如有 |

## 4. 构建 / 运行 / 测试

**Maven 不在 PATH 上**，用心自带的：

```powershell
$env:JAVA_HOME="C:\Program Files\Java\jdk-17"
$mvn = "C:\Program Files\JetBrains\IntelliJ IDEA 2026.2.0.1\plugins\maven-plugin\lib\maven3\bin\mvn.cmd"

cd D:\moodsite\windows
& $mvn test        # 当前 16 个测试（SyncEngineWatchTest 9 + UpdaterAboutTest 7），0 失败
                   # 注意 -q 会把汇总藏起来，去 target\surefire-reports\*.txt 看
.\package.bat      # Windows 打包：jpackage + WiX → target\dist\XinLv\ 与 XinLv-<版本>.exe
```

```powershell
# macOS：在局域网 Mac 上构建（本机不行）
cd D:\moodsite
python -X utf8 build_macos.py
# 它会把源码同步到 Mac、跑 ./build.sh，**并把产物拉回 D:\moodsite\deliver**
```

> `package.bat` 结尾有 `pause`，非交互跑要喂 NUL（`cmd /c "package.bat < NUL"`）。
> 它从 `pom.xml` 读版本号，不要在里面硬编码版本。

## 5. 调用的服务端接口

**两个服务端，别搞混：**

### ① 心履自己的服务端（`https://xin-lv.com`，Django）

| 用途 | 端点 | 认证 |
|---|---|---|
| 探活 | `GET /api/v1/ping/` | 免 |
| 注册 / 登录 / 注销 | `POST /api/v1/register/`、`/login/`、`/logout/` | Bearer |
| 拉取 / 推送心情记录 | `GET /api/v1/sync/pull/?since=`、`POST /api/v1/sync/push/` | Bearer |
| **长轮询** | `GET /api/v1/sync/watch/?since=` | Bearer |
| 内容目录 / 推荐 / AI 树洞 / 资料 | `/api/v1/catalog/`、`/recommend/`、`/chat/*`、`/profile/` | Bearer |

认证是 `Authorization: Bearer <ApiToken>`。权威文档：`D:\moodsite\web\docs\心履API文档.md`。

### ② phix 服务端（`https://phix.ing`，Django）

统一账号、资料对象同步、跨站免密登录（`/auth/sso/*`）、以及**应用内更新检查**：
`GET /api/v1/update/check?product=xinlv&platform=win|mac`。

权威文档：`D:\phix\server\docs\协议规范.md`、`D:\phix\server\docs\同步实时化.md`。

### 长轮询最容易写错的一条

`changed=false` 有**两种含义相反**的情况，HTTP 层长得一模一样：

- **没有** `retry_after` → 正常挂满 25 秒超时 → **立刻**再挂（长轮询接力）；
- **有** `retry_after` → 服务端同时挂起的名额满了 → **必须先等**再挂。

把前者当后者会丢延迟，把后者当前者会**热循环打服务器**。
另外客户端的**读超时必须大于服务端的 25 秒挂起**（现在给 35 秒）。

## 7. 开发思路与约定

- **注释和提交信息用中文**，写**为什么**。
- **网络调用一律走 `Bg.run`**，绝不在 JavaFX 界面线程上做 I/O（会卡住窗口）。
- **外链用代码库既有的 `Desktop.browse(URI)` 模式**打开默认浏览器，
  失败要有兜底提示（"打不开浏览器，请手动访问：…"）。
- 更新检查要有**三态**：`UP_TO_DATE` / `NEW_VERSION` / `FAILED`，
  且**失败绝不能显示成「已是最新版本」**。
- 发现新版本时用 `CARD_IN_FLIGHT` 之类的标记与启动检查互斥，**不要叠出两张卡片**。
- 测试风格：把网络与时间做成**可注入的桩**，纯逻辑单独测（见 `SyncEngineWatchTest`、
  `UpdaterAboutTest`），不碰真网络。
- 改完共有文件后，**把另一平台的副本同步过去并核对哈希一致**。

## 8. 已知的坑与禁忌

1. **`APP_VERSION` 必须与 `pom.xml` 的版本一起改**，否则更新检查永远觉得"要更新"。
2. **两个仓库会漂移**：改完一边一定要同步另一边（曾出现过 macOS 那份多一行重复
   `import` 的情况）。
3. **「关于软件」的"检查失败"不能当"已是最新版本"**。
4. **`package.bat` 结尾的 `pause`** 会挂住无人值守的构建。
5. **jpackage 的版本号来自 `pom.xml`**，`package.bat` 里硬编码版本曾经导致
   构建后找不到 jar 而失败（注释里记着）。
6. **macOS 产物未签名**：用户需右键 →「打开」一次。
7. macOS 产物**必须**在 Mac 上构建；`build_macos.py` 会把产物拉回 `deliver\`
   （这一步以前缺失，导致本地 `deliver\` 一直是上一版 —— 已修）。
8. 写 PowerShell 脚本要**带 UTF-8 BOM**。
